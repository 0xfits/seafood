| id | group | expect | actual |

| H5 | httpLive | ★ 5 新口无 token ⇒ 逐口 401 | `{"no_token":{},"err":"fetch failed"}` |

### 1.2 根因（判据：夹具隐式取自增主键，与全局 identity 序列失配）

**关键事实（活体取证）**：
```
表 job_submission：count=40，max(submission_id)=247
序列 job_submission_submission_id_seq：last_value=245，is_called=true，cache_size=1
⇒ 下一次 nextval = 246；而 246 与 247 已存在于表内（历史探针提交）
```
**精确复现**（临时探针复刻门里那条 INSERT，`pre/probe-repro.txt`）：
```
code=23505  detail="Key (submission_id)=(246) already exists."
message="duplicate key value violates unique constraint \"job_submission_pk\""
```

**机制链**：
1. `migrations/0014_job_flow.sql:116`：`submission_id bigint GENERATED BY DEFAULT AS IDENTITY`（PK `job_submission_pk`）。
2. 门夹具（原 `p8-s8:582`）INSERT **不写** `submission_id` ⇒ 取号完全依赖**全局** identity 序列。
3. identity 序列推进**不随事务 `ROLLBACK` 回退**（PG 语义）。历史探针把 id=245/246/247 **提交**进表，而其序列停在 245 ⇒ **表内 max(247) ≥ 序列 next(246)** —— 隐式取号必撞 PK。
4. 命中后 `withTransaction` 整体 `ROLLBACK`，异常冒泡到门里的 `catch`（原 `p8-s8:721-724`），被记为 **id=`V1`**。

**同族征兆（同一机制在别表的可见化身）**：本门自身每跑一次，`rating_id` / `event_id` 序列都会前进（因为 `src/database.ts` 的 `submitRating` / `transitionListingOrder` 同样隐式取号），即使整事务回滚——实测 `rating`/`listing_order_event` 两表 **count=0** 而序列已到 **342**（`pre/probe-seqs.txt`）。这正是「序列推进不随 ROLLBACK 回退」的表征。

**★ 附加发现（红点非稳定，属同一缺陷的“抖动”面）**：失败的隐式取号**仍会消耗** `nextval` ⇒ 连跑时序列向 max 逼近，**无需改任何代码**红点会自愈。实测连跑两次（改前）：
```
run 1: total=74 passed=70 failed=4   V1=job_submission_pk   （序列 246→247）
run 2: total=92 passed=89 failed=3   V1=pass=true           （序列 247→248，取到空闲 248）
```
⇒ 该 `V1` 红点的**存在依赖全局序列与表内 max 的相对位置**（一个与门无关的外部状态），非常数。这一点是「必须根治、不能靠重跑碰运气」的直接论据。

## §2 修法与为何选该锢

### 2.1 修法（只改 `scripts/**`，3 处夹具 INSERT）

把本门夹具里**依赖自增主键的三处隐式取号**改为**业务语义锢 = 取自门内既有的固定保留窗口（≥900000）**：

| # | 表 | 原（隐式取号，依赖序列） | 改后（显式保留 id） |
|---|---|---|---|
| ① | `job_submission` | `INSERT (job_id, worker_uid, …)` | `submission_id = 900901` |
| ② | `listing_order_event` | `INSERT (order_id, event_type, …)`（4 行） | `event_id = 900921 / 922 / 923 / 924` |
| ③ | `rating` | `INSERT (rater_uid, ratee_uid, …)`（4 行） | `rating_id = 900911 / 912 / 913 / 914` |

该窗口与门内既有先例**同族同段**：uid `9810xx`、`job` `900001/900002`、`listing_order` `900201-900205`、`rating.target_id` `900011-900014` —— 全部是**固定、保留、不撞号**的夹具 id。改后夹具对这些表**不再触碰任何全局序列**。

### 2.2 为何选「显式保留窗口」而不是「插入后读回真实 id」

任务只允许两类修法：① 定位改**业务语义锢**；② 若语义确实需要「新插入行的 id」则**先插入、读回真实 id**。

- **本门语义不需要那三行的自增 id**。夹具的语义定位键早已是业务键：`job_submission` 靠 `(job_id=900002, worker_uid=981012) + create_key='p8s8:s2'`（供 T1/T2 时效 V9 用）；`listing_order_event` 靠 `order_id + idempotency_key='p8s8:eN' + time_created`（供 T3/T4 · V10）；`rating` 靠 `(rater_uid, target_type, target_id)` 唯一键 + `idempotency_key='p8s8:r:x'`（供四周期聚合 V5）。**没有任何断言读取这三处的主键值**。
- **选 ① 而非 ②**：修法②「读回真实 id」**治不了撞号**——撞号发生在*隐式取号那一刻*（值已被占用），读回的前提是插入先成功。修法②只适用于「插入成功但需要那个新 id 去断言」的场景（本门不是）。
- **沿既有先例（避免重复手写）**：仓库共享分配器 `scripts/ns-alloc.ts` 是**只读扫描活体命名空间**的分配器（uid 窗口 / 币符号 / 幂等键前缀 / job 号段），面向**提交型**探针；本门是**回滚型夹具**，其先例就是门内既有的**固定 ≥900000 窗口**（`9810xx / 9000xx`）。故把 identity PK 也纳入该固定窗口，是本仓先例的正向延伸，无需也不宜另造分配器。

**★ AC1 偏差（必须点明）**：本单 AC1 预期「改后 = `71/74`（V1 转绿；其余 3 红 http）」。**实测不是 71/74，而是 `92/89/3`**。原因（已实证）：

- 夹具修好后事务跑到底，18 条检查全部产生 ⇒ 总数回到 **92**。
- **「3 红」与 AC 一致**（就是 H5/H6/H7 三条 http 腿）。分歧仅在**分母**：AC 把「崩溃态总数 74」误当成了健康态总数。这不是没修好，而是修好后总数**本来就该是 92**。两次连跑均 `92/89/3`（AC4 的“两次一致”成立）。

### 3.2 判负（两法，均红→绿）

**判负-1 · 硬编码已占用自增 id 246**（临时把 `submission_id` 改回 `246`）：
```
改后-红:  SUMMARY total=74 passed=70 failed=4    V1 pass=false actual="…job_submission_pk"
复原后  :  sha256 = c26a7b318e1a71ffa212f76930c50e8da899abb771af841a1662d9c528edd069
改后-绿:  SUMMARY total=92 passed=89 failed=3    V1 pass=true
```

**判负-2 · 差分法（“人为推进序列”把序列压到表内 max 之下）**——同一条滞后序列下对拍「改后夹具 vs 旧夹具」：
```
STEP 2a  setval('job_submission_submission_id_seq', 246, true)  ⇒ 序列 248→246（next=247，已被占）
STEP 2b  改后夹具（显式 900901）跑门  ⇒ 仍绿 total=92 passed=89 failed=3   ★ 对序列漂移不敏感
STEP 2c  临时改回旧形（隐式取号）跑门 ⇒ 红   total=74 passed=70 failed=4   V1=job_submission_pk
STEP 2d  复原夹具 + setval 回 248    ⇒ sha256 与改后逐字节相同 · 再跑门绿 total=92 passed=89 failed=3
```
⇒ 判负-2 是「根治」的强证据：**在完全相同的滞后序列状态下**，旧夹具必红、改后夹具必绿——证明红点已被**结构性解除**，而非靠序列偶发对齐。

主仓零残留：改后脚本 sha256 `c26a7b31…` 与判负前后一致；DB 端 `baseline == after_rollback`（§3.1）。
