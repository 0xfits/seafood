## 诚实清单（未验证 / 已知张力 / 判负方式的边界）

1. **M6 的判负对照不是 spec CR67 字面形态**：CR67 要求「把 `ON CONFLICT DO NOTHING` 换成先查后插 ⇒ 必须双发」。那需要改 `ledger_post_event`（`0004`/`0005`）——**越界**（裁定 #14 明令禁止改函数体）。本单的等价对照 = 「同 business 内容 + **每请求不同键**（= 没有共享幂等探针）⇒ 3 个独立事件、3 次支付」（读数见 `5b_m6_negative_control`）。**该对照证明「多发只可能来自缺少共享键」，但不能证明「换掉 ON CONFLICT 会双发」**。
2. `W = 0`（前 M 层权重全零）的**运行时**分支**不可达**（`0007` 写入守卫已拒，裁定 #16）⇒ 本单只做了「政策写入档 = 400」的取证（`6b_app_layer_negatives.policy_guard_negatives`）。**口径张力已登记**：§13.2 #10 写 400 / §14.2 #2 读 500；本实现运行时取 **500 defect**（`LEDGER_FEE_RATE_INVALID` + `POLICY_WEIGHTS_ALL_ZERO`），已写进 `src/commission.ts` 注释。
3. **`request_fingerprint` 的覆盖面是设计选择**：`settleJobFingerprint` 只覆盖 business 字段（job_id / employer / worker / cid / gross），**不含金额派生量**。⇒ 政策改版后「重算同键再发」走**重放分支**（读数 `step4b_replanned_under_new_policy: {ok:true, replay:true, fee:"500"}`），**不产生 409**。与 CR26②「重放须复用同一 payload/指纹」自洽，但 spec §5.1 的「规范化请求体」范围**需要 Zang 一句话确认**。
4. **TOCTOU 面保留**（CR26① / 裁定 #14：计算不下沉）：本探针是**单进程串行**跑各用例，未构造「政策正在改版 + 并发重试」的竞态取证。
5. **构图的插入顺序有硬要求**（本单实测）：`depth := 1 + COALESCE(depth(父),0)` 只在插入那一刻算 ⇒ **必须先插「更深的边」（父行先存在）**；反过来插会让 13 行 `depth = 1` 且 `bad_depth = 13`（首轮真实读数，已用 `p2d-01` 修复）。这是 spec §3.2「既有边会被后来的插入追溯破坏」的机械复现，**建议写进 spec 的绑定协议（CR16/§3.3）**，否则每个消费方都要自己踩一次。
6. **未做 HTTP/路由层集成**：本单交付 = 服务层模块 `src/commission.ts` + 探针；`api/`、`frontend/` 未动。错误面一律取 `err.httpStatus`（`status ?? 500`），**未使用 `err.status`**（§11 R88 的脚本退出码语义保持不动）。
7. **`job_payout` 的前置托管用 `op=hold`（kind `hold`）**，形状对齐 `scripts/p2b-02-cases.ts`；未验证「必须由 `job_escrow` 冻结」这类 P3 约束（P3 才有 `job` 表）。`ref_id` 用自造数值 job_id（spec §70⑤：P2 阶段 `ref_id` 不是 FK，DB 不校验存在性）。
